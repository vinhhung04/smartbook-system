# Financial settlement migration preflight

Migration: `20261118010000_financial_settlement_integrity` (Borrow only).

- Purpose: preserve verified provider receipts separately from the current fine obligation; retain unapplied money for manual reconciliation, and persist counter-payment request identities/results.
- Schema: two new tables, `provider_payment_settlements` and `fine_payment_requests`; unique intent/provider transaction identity and request key; positive/conservation checks; append-only triggers. No existing columns, rows, fine/deposit policy or payment history are changed.
- Data impact/backfill: new tables initially empty. Historical SUCCESS/FAILED/EXPIRED intents remain unchanged; no invented provider evidence or automatic historical allocations/refunds. Existing unresolved provider receipts require provider reconciliation. Legacy retries without keys can use a nonempty transaction reference scoped to actor/fine/method; identity-less staff payments return400.
- Lock impact: CREATE TABLE/index/trigger on new empty tables; brief referenced-table locks for foreign keys to existing intent/fine/customer tables. No existing-table rewrite/index build or historical row scan. Rehearse with lock_timeout5s and statement_timeout30s. Serialize app fine writers on customer before fine/item/deposit/wallet locks.
- Compatibility: additive SQL is readable by old app; old app does not enforce the new receipt/idempotency semantics and must not run financial writers after new app opens traffic. Prisma Client must be regenerated from the same schema before app deploy. Deploy financial workers in a coordinated maintenance window.
- Verification: inspect pg_tables/pg_indexes/pg_constraint and new append-only triggers; compare existing fine/payment/intent counts and sums before/after; check no new rows on migration; run exact Node20 real-PG settlement/idempotency/concurrency regressions and all historical Borrow tests.
- Read-only checks: `SELECT status,count(*) FROM fine_payment_intents GROUP BY status; SELECT count(*),sum(amount) FROM fine_payments; SELECT count(*) FROM provider_payment_settlements; SELECT count(*) FROM fine_payment_requests; SELECT conname,pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid IN ('provider_payment_settlements'::regclass,'fine_payment_requests'::regclass);`
- Rollback/forward-fix: retain additive tables and immutable receipts/results. Never drop/reset/delete financial history. Before new writes, compatible app fallback may ignore empty tables; after new writes use forward-fix with reconciliation. Database restore is separate coordinated disaster recovery and cannot undo money collected by a provider.

Execution authorization is limited to the independently verified loopback PostgreSQL audit database `127.0.0.1:25432/borrow_audit`. No production migration or real payment/refund is authorized or executed.

Legacy counter-payment cutover: a reference-only request with no durable request result that matches a pre-existing payment on the same fine/method returns409 `LEGACY_PAYMENT_REVIEW_REQUIRED`, before accrual or another allocation. It neither fabricates an original response nor allocates that partial payment again. New reference-only operations still work when no matching history exists; new keyed requests use the persisted fingerprint/result. References remain nonunique across different fines. Staff must reconcile historical evidence before intentionally creating any additional payment.
